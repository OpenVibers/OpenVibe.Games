# Instances in one server process

Set `GAMES_INSTANCES_PER_PLACE` above its default of `1` to let a place run several rooms in one server process. Each room has its own simulation, players, world entities, constraints, clock, and write-behind queue. `MAX_PLAYERS` is the capacity of **each** room. A join uses the first running room with capacity, then starts another room up to the configured maximum. The first room retains the existing place rows; later rooms use instance-scoped state rows. Characters, inventory, skills, and the map definition are shared by place. Each character also keeps a last position in every room it visits.

The server registers room slots as `placeId:slot` in PostgreSQL `game_instances`. A claim starts in `starting` with a 60-second boot lease, becomes `running` after the world loads, changes to `draining` during shutdown, and ends `stopped`. The process renews each 15-second running lease every 5 seconds. An expired room can be claimed by a new holder; every claim increments its lease version. The write-behind transaction checks and locks the holder/version row before committing game state, so a former holder cannot commit after its lease is replaced. A room whose renewal fails stops ticking and closes its clients. PostgreSQL is the lease authority; Valkey continues to serve only the existing optional ticket and rate-limit roles.

The Players tab lists room buttons when multiple rooms are enabled. Transfer is a validated `transfer` intent with a destination `instanceId`. The server checks that the target belongs to the same place, is in range, is running, and has capacity before leaving the source. It flushes the character before joining the target on the same authenticated WebSocket connection. The original single-use upgrade ticket is never reused, and the destination repeats the definition digest check. A refused transfer keeps the source session. Protocol v22 adds the transfer message and optional room fields in `welcome`; v21 clients can still join and play. With the default single room, `welcome` has no room fields and transfers are unavailable.

`GAMES_INTEREST_CELL` sets the ground-plane spatial hash cell width in metres (default `16`). `GAMES_INTEREST_RADIUS` sets the enter radius (default `80`; legacy `INTEREST_RADIUS` still works). Each client tracks the cells intersecting its interest area; crossing cell boundaries refreshes its subscriptions and sends spawn/despawn differences. A known entity leaves at 110% of the enter radius, avoiding churn near the edge. Awake-body updates use subscribed cells and a precise distance check.

The socketless probe is `node --import tsx apps/server/scripts/instanceLoad.ts 4`; `--baseline` uses direct M3-style routing. It joins clients, drives movement for 90 ticks amid 400 spread entities per room, transfers one player out and back, and reports mean/p95 tick time and bytes per client. The two-client test uses conservative timing headroom because scheduler and WASM warmup vary; it keeps a tighter bandwidth bound.

Scope: one server process now hosts separate Scraplandia and Salvage Rush room hubs. Room routing and transfer stay within the joined place and this process. A second process or host cannot accept a handoff yet; region routing across hosts and cross-process transfer tokens remain future work. The room registry is shared in PostgreSQL, but this release does not direct a client to a remote process.
